## Affected Pages/Routes

- `/` (the single Streamlit page) — the whole dashboard. There is no router; every
  interaction happens on one page via widgets and reruns.

## Key Interactions to Verify

- **Borough toggle, reported vs recovered.** The core of the finding. Switching must change
  the borough bar chart's values AND the `n excluded` annotation. Verify the recovered view
  shows more rows than the reported view, and that the three-way slice (reported /
  recovered-surface-street / recovered-highway) is visible rather than collapsed into one
  corrected number.
- **Date range picker.** Bounds must derive from `max(crash_date)` in the data
  (2026-06-11), never from today. Verify you cannot select a range that returns zero rows.
- **Snapshot line.** Must render a static "data through 2026-06-11, pulled 2026-08-08"
  string. Verify it does NOT make a network call, and does NOT display an ever-growing
  "stale by N days" counter.
- **Chart filters generally.** Changing borough, factor, or victim type should update every
  dependent chart consistently. All nine charts read from one shared filtered VIEW, so a
  filter change must propagate everywhere or nowhere.

## Edge Cases

- **Zero-result filter.** Pick a borough + factor + date combination with no matches. Charts
  should show a deliberate empty state, not an exception or a blank canvas.
- **Missing `crashes.parquet`.** Rename the file and load the app. Must show a friendly
  message, not a Streamlit traceback.
- **Scatter and geo-density at full row count.** These are the two charts that can hang the
  *browser* (a separate limit from the ~1 GB container ceiling). Verify they aggregate or
  sample rather than plotting 848,742 raw points.
- **Rapid filter changes.** Move a slider quickly several times. DuckDB connection reuse
  across Streamlit reruns is the classic failure point; watch for intermittent errors.
- **First paint on a cold container.** Community Cloud sleeps after 12 hours idle. Verify
  cold start completes and does not attempt any network fetch.
- **Mobile viewport (375x812).** Nine charts on a phone. Verify nothing overflows
  horizontally.

## Critical Paths

1. **Load → read the finding → understand it.** A visitor lands, sees the headline finding
   (that the standard borough chart drops ~40% of NYC traffic deaths), and can reach the
   evidence without hunting. Information hierarchy: finding first, chart gallery second.
2. **Load → toggle borough source → see the numbers move.** The single interaction that
   proves the project's claim. If this is broken or unconvincing, nothing else matters.
3. **Load → pick a filter → every chart agrees.** Cross-chart consistency is what separates
   a dashboard from nine unrelated plots.

## Notes for the tester

- The app is read-only. No auth, no writes, no user data, no forms. Security surface is
  limited to SQL construction: verify filter values are parameterized, never f-string
  interpolated into DuckDB queries.
- The upstream feed is 58 days stale by design (NYC's updater, not a bug in this app).
  Charts ending 2026-06-11 are correct, not broken.
