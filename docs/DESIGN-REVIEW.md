## Problem Statement

Build the NYC Motor Vehicle Collisions dashboard described in `PROJECT_GUIDE.md` as a
portfolio piece for entry-level data analyst applications, while the guide itself is
written as a GitHub-practice curriculum. Those two goals want different things, and the
guide's plan does not currently survive contact with either the data or GitHub's limits.

Three concrete gaps, all measured this session:

1. **The scaffold the guide assumes does not exist.** `files.zip` contains exactly two
   files: `PROJECT_GUIDE.md` and `audit_columns.py`. Every artifact later phases depend
   on (`scripts/pull_data.py`, `app/streamlit_app.py`, `requirements.txt`, `.env.example`,
   `README.md`, `DATA_DICTIONARY.md`) has to be written from scratch. The cloned repo has
   **zero commits**.
2. **The working sample is unusable.** 8,000 rows, of which **7,146 (89.3%) are from
   2021**, because the original Socrata request had no `$order` and got storage-order
   rows. Every time-based chart in the roadmap is meaningless on it.
3. **The guide's own plan cannot execute.** Phase 4 pulls 2019-2025 (812,318 rows,
   ~189 MB as CSV) and Phase 10 deploys from the repo. GitHub hard-blocks files over
   100 MB. The guide never specifies how the app gets its data.

And underneath all three, the real problem: a nine-chart dashboard on a public dataset
makes no claim, so there is nothing for anyone to ask about.

## Target User & Narrowest Wedge

**Target user:** the person who already has the interview and clicks the link during or
after it. Not the resume screener, who statistically will not click.

**Narrowest wedge:** one sentence that survives being read out loud.

> The borough bar chart that appears in every NYC crash dashboard silently drops 30% of
> crashes and 40% of the deaths, and 70% of those rows can be recovered from coordinates.

Everything else in the project is evidence for that sentence.

### The finding, verified against all 2,269,187 rows

| | rows | deaths | fatality rate |
|---|---|---|---|
| Borough **labeled** | 1,577,812 | 2,176 | 1.379 / 1,000 |
| Borough **NULL** | 691,375 (30.5%) | 1,441 | **2.084 / 1,000** |
| ratio | | **39.8% of all deaths** | **1.51x** |

The cause is visible in the street names of the unlabeled rows: BELT PARKWAY (13,399),
LONG ISLAND EXPRESSWAY (9,777), BROOKLYN QUEENS EXPRESSWAY (9,646), GRAND CENTRAL PKWY
(8,431), FDR DRIVE (7,264), CROSS BRONX EXPY (6,040), MAJOR DEEGAN (5,819), CROSS ISLAND
PARKWAY (5,675), VAN WYCK EXPWY (5,304). Limited-access highways, outside precinct
street-grid geocoding.

**It is fixable, not merely complainable-about: 487,159 of the 691,375 unlabeled rows
(70.5%) carry usable coordinates** and can be assigned a borough by point-in-polygon join
against NYC borough boundaries.

### Why saturation is the precondition, not the obstacle

This claim is only meaningful *because* hundreds of dashboards draw that chart. On an
exotic scraped CSV there is no genre to indict. The saturation is the subject matter.

### Prior art (checked, and it is favourable)

- **[AEE Law](https://aeelaw.com/data/belt-parkway-crash-data/)** made the observation for
  one road: *"The borough field is blank for 98.7 percent of Belt Parkway rows. That's
  almost certainly a geocoding gap for a limited-access highway, not a real signal, and
  we don't report a borough comparison from it."* They saw it and explicitly declined to
  go further.
- **[Aleksey Bilogur's 2016 notebook](https://github.com/ResidentMario/motor-vehicle-collisions)**
  (author of `missingno`, 4.2k stars, the closest prior-art risk) counted 184,301 missing
  boroughs (~24% at the time) and performed **no analysis of them**. He listed geocoding
  recovery as an approach and never implemented it.

Unclaimed: the citywide quantification, the fatality differential, and the actual
recovery. Cite both predecessors. Being second on the observation and first on the fix is
a stronger, more honest position than claiming discovery.

### Two supporting findings that come free

**1. The obvious trend chart lies.**

| year | crashes | injuries | deaths |
|---|---|---|---|
| 2019 | 211,486 | 61,391 | 244 |
| 2025 | 85,546 | 49,634 | 229 |
| change | **-59.5%** | -19.2% | **-6.1%** |

Injuries per reported crash went from 0.290 to 0.580, a doubling. Deaths per 1,000
reported crashes went from 1.154 to 2.677. A monthly-volume line chart invites the
reading "NYC streets got 60% safer," which the fatality data does not support. The
denominator changed, not the danger.

**2. The existing cleaner already beats the clones.** The API returns `"BELT PARKWAY"`
padded and unpadded as two distinct values (13,399 and 6,889). Every naive "Top 5
dangerous streets" chart double-counts it. `clean_crash_data.py:70` already strips
whitespace.

## Constraints

Measured this session, not assumed.

**Data size** (compression measured on a 5,000-row 2023 sample; a multi-year file will
run slightly larger):

| range | rows | CSV | Parquet+snappy | Parquet+zstd |
|---|---|---|---|---|
| 2019-2026 | 848,742 | 198 MB ❌ | 45 MB ⚠️ | **35 MB ✅** |
| full 2012-2026 | 2,269,187 | 529 MB ❌ | 121 MB ❌ | 93 MB ⚠️ |

GitHub warns at 50 MB and hard-blocks at 100 MB per file. Parquet with zstd is what makes
this project physically possible.

**Data freshness.** `rowsUpdatedAt` = 2026-06-15. Latest `crash_date` = 2026-06-11.
Today = 2026-08-08. **The feed is 58 days stale.** A dashboard that silently shows a
two-month gap looks broken; one that surfaces it looks operationally aware.

**Dataset span.** 2012-07-01 to 2026-06-11. 2012 is a partial year (100,545 rows) and
should be excluded from any per-year chart, or annotated.

**Full table vs the 2019-2026 pull — keep these straight.** The finding is computed
against the whole table via the API; the app ships the recent subset. Mixing the two is
the easiest way to put a wrong number in the README.

| | full 2012-2026 | 2019-2026 pull |
|---|---|---|
| rows | 2,269,187 | 848,742 |
| deaths | 3,617 | 1,945 |
| borough NULL | 691,375 (30.5%) | 269,811 (31.8%) |
| recoverable from coordinates | 487,159 (70.5% of NULL) | 221,658 (**82.2%** of NULL) |

The recovery rate is *higher* in the recent subset (82.2% vs 70.5%), because coordinate
capture improved over time. Worth one sentence in the writeup: the fixable share of the
problem is growing, so the standard borough chart is getting more wrong, not less.

**Environment.**
- Python 3.12.10, reachable **only as `py`**. The `python` on PATH is the Microsoft Store
  stub that prints an install message and exits. Any docs or scripts must say `py`.
- pandas, streamlit, plotly: **not installed**.
- `uv` is available and is the fastest path to an environment.
- **TLS interception on this network**: `uv` needs `--system-certs` to reach PyPI. `curl`
  to Socrata works fine (HTTP 200 in 0.42s), so the API pull is unaffected.

**Repo structure.** `files/` is nested inside an unrelated umbrella git repo
(`D:/GitHub Projects`, remote `Jeffreys-World/GitHub`). The project's own clone sits one
level *below* the working files and has zero commits. Git commands from the working
directory resolve to the umbrella repo. This must be fixed before the first commit or
work will land in the wrong repository.

**Existing assets worth preserving.** `clean_crash_data.py` (140 lines) is the strongest
code in the project: coordinate bounds-checking, Excel-serial date handling, a
machine-readable cleaning log, whitespace normalization, and an explicit refusal to guess
missing boroughs (`# leave missing as missing (do not guess)`, line 73). Lines 74-84
already compute `borough_missing_but_recoverable_via_lat_long`. **The finding was already
instrumented; only the writeup was missing.**

## Approaches Considered

### Approach A: Committed Parquet + DuckDB — **SELECTED**
One ~35 MB zstd Parquet file in the repo. Every chart is a versioned `.sql` file executed
by DuckDB against it.
- **Pros:** `clean_crash_data.py` and `audit_columns.py` both survive untouched; Streamlit
  Cloud reads the file straight from the repo so Phase 10 deploy has no runtime API
  dependency to fail during a demo; the point-in-polygon recovery runs locally against the
  full table.
- **Cons:** a 35 MB binary lives in git history permanently, and every re-pull adds
  another blob that cannot easily be removed later.
- **Effort:** M (human ~2 days / CC ~1-2 hrs) · **Risk:** Low · **Completeness:** 9/10

### Approach B: Aggregate marts + sampled detail
Commit only pre-aggregated tables (month, borough, factor, hour x day) plus a
coordinate-sampled detail table. Full Parquet gitignored and regenerable.
- **Pros:** genuinely the better architecture; a semantic layer of marts is a more senior
  skill than querying one flat file; 2-5 MB repo loads instantly.
- **Cons:** geo density and crash-location scatter need individual rows, so two of the
  nine roadmap charts run on a disclosed sample; more moving parts to get wrong while also
  learning the git workflow, which raises abandonment risk on a project whose main virtue
  is being finished.
- **Effort:** L (human ~4 days / CC ~3 hrs) · **Risk:** Med · **Completeness:** 7/10

### Approach C: Live SoQL against the API
No committed data; cached SoQL queries at runtime.
- **Pros:** zero repo size; SQL is the entire product; freshness banner is native.
- **Cons:** **the borough-recovery finding cannot be computed in SoQL** because
  point-in-polygon needs local geometry, which kills the project's only argument; the app
  breaks whenever Socrata is down or rate-limits, which means a demo failing live in front
  of the one person who finally clicked; discards `clean_crash_data.py` entirely.
- **Effort:** M (human ~2 days / CC ~1.5 hrs) · **Risk:** High · **Completeness:** 6/10

## Recommended Approach

**Approach A.** Selected by the user.

It fits git, keeps the best code already written, and makes SQL real without adding a
failure mode. The reframe that makes the whole project work: it stops being "I built a
dashboard of NYC crash data" and becomes **"I found that the standard borough chart on
this dataset drops 40% of the deaths, proved it on 2.27M rows, recovered 487,159 of the
missing labels from coordinates, and built the dashboard that shows both versions."**

The second claim is harder to fake, and it is the same move as the triage console: report
the number that makes the pretty chart worse. Two projects with one thesis about the
author beats four unrelated artifacts.

### CEO review decisions (2026-08-08, HOLD SCOPE + packaging)

Four decisions settled by `/plan-ceo-review`. They amend the phases below.

1. **The point-in-polygon join runs OFFLINE, never at runtime.** `borough_recovered` and
   `borough_source` are written into the committed Parquet by the pipeline. The deployed
   app reads them as ordinary columns. No DuckDB `spatial` extension, no geopandas, no
   network call at cold start. This removes the only runtime dependency that could fail
   in front of a visitor.
2. **pytest, with regression tests aimed at the bugs that actually happened.** Minimum
   three: (a) the pull's year distribution is not concentrated in a single year, which
   locks the `ORDER BY` bug shut permanently; (b) `clean_crash_data` handles API-format
   input, not just the Excel sample; (c) the borough split reproduces the 1.51x fatality
   ratio.
3. **Harden `clean_crash_data.py` and drop the `location` column.** The zip coercion at
   lines 79-81 (`str(int(v))`) must not raise, or one malformed value out of 848,742 kills
   a 20-minute pull at its final step. Guard the dtype branches against a missing column.
   Drop `location`: it is redundant with `latitude`/`longitude`, no chart in the roadmap
   reads it, and its embedded newlines are what make CSV line counts overcount records by
   2.9x.
4. **Clamp date ranges to the data's real max, plus a freshness banner.** The feed is 58
   days stale. Derive picker bounds from `max(crash_date)`, never from `today()`, so a
   visitor cannot select an empty range and conclude the app is broken.

Plus the Approach B packaging, to be done before the first commit where possible: repo
description carrying the finding and a number, topics, homepage set to the live Streamlit
URL, a project `CLAUDE.md` fixing commit conventions, and a GitHub Action running
`audit_columns.py` on push.

### Outside-voice amendments (same session, all accepted)

5. **Deploy moves to Phase 1, and the repo rename happens BEFORE the first push.**
   Streamlit derives the app URL from the repo name, so renaming after the link exists
   breaks the link. Phase 1 pushes a hello-world `app/streamlit_app.py` and deploys it.
   Every later phase is then an increment on a live thing, and deploy risk (dependency
   hell) surfaces on day one rather than after a week of sunk work. Do not share the URL
   until there is something behind it. **This supersedes the Phase 9 deploy ordering.**
6. **487,159 and 221,658 count rows WITH COORDINATES, not rows that matched a polygon.**
   Do not use them as acceptance criteria. Measure the actual join yield and record it.
   Also: NYC publishes borough boundaries water-included and shoreline-clipped. Choose
   deliberately and state which, because the clipped version drops exactly the
   water-adjacent highway rows (Verrazzano, GWB, Cross Bay, Marine Parkway, the Belt) that
   this recovery exists to capture.
7. **Validate the recovery method against known-good labels.** 1,577,812 rows carry both a
   reported borough and coordinates. Run the same point-in-polygon on those and report the
   agreement rate in `docs/FINDING.md` and Success Criteria. Same code, different row

   chart" ships an unvalidated borough chart.
8. **Report the recovery as a three-way slice: reported / recovered-surface-street /
   recovered-highway.** Collapsing it into one corrected ranking makes the chart rank
   boroughs partly by limited-access highway mileage, which is not what a reader of a
   borough safety chart believes they are seeing. The split is also the more interesting
   result. This replaces "a ranking change is a stronger headline" in Open Question 1.

Smaller amendments, folded in without a separate decision:
- **Commit the Parquet once, not twice.** Gitignore it until after the borough recovery

### Eng review decisions (2026-08-08, FULL_REVIEW)

Three findings from `/plan-eng-review`, all accepted.

9. **`clean_crash_data.py:115` is a silent data-loss trap. Fix it and make it fail loud.**
   `df = df[[c for c in col_order if c in df.columns]]` is an allowlist: any column not
   named in `col_order` is dropped without error. `borough_recovered` and `borough_source`
   are not in the list, so re-running the cleaner after the recovery would silently delete
   the finding's own columns. Add both columns, remove `"location"` (decision 3 above never
   takes effect otherwise), and change the filter to RAISE on unexpected columns rather
   than dropping them. **A regression test for this is CRITICAL and non-optional** (iron
   rule: it is a change to existing behavior with no coverage).
10. **Use Streamlit's `st.connection` / `BaseConnection` for DuckDB**, not a hand-rolled
    module-level singleton. The framework built-in manages the connection lifecycle across
    reruns, which is the specific thing hand-rolled versions get wrong and which surfaces
    as intermittent errors under rapid filter changes. [Layer 1], do not reinvent.
11. **One shared DuckDB `VIEW` carrying the common filter predicates**, with each chart
    query selecting from it. Nine `.sql` files each repeating the date-range,
    borough, and `has_valid_location` predicates means one filter change becomes nine
    edits, and they will drift.

### Eng outside-voice amendments (all accepted) — SUPERSEDE earlier decisions

12. **Use the paginated `.csv` RESOURCE endpoint, NOT the bulk export.** This reverses the
    earlier "bulk CSV preferred" amendment. The bulk export
    (`rows.csv?accessType=DOWNLOAD`) returns a completely different schema:
    `CRASH DATE,CRASH TIME,BOROUGH,...` uppercase with spaces, `COLLISION_ID` already
    underscored, dates `MM/DD/YYYY`. The resource endpoint returns the snake_case ISO-date
    schema `clean_crash_data.py` already speaks. `.lower().replace(" ","_")` does NOT
    reconcile them, because the API is internally inconsistent (`vehicle_type_code1` vs
    `vehicle_type_code_3`). Pagination was never the problem: `$offset=2,200,000` returns
    in 1.04s, measured.
13. **Three real bugs in `clean_crash_data.py`, all on the production path:**
    - **Latitude/longitude are never coerced to numeric.** Only `COUNT_COLS` gets
      `pd.to_numeric` (line 104). The API returns numerics as strings, so line 91's
      `df["latitude"] < NYC_LAT_RANGE[0]` is `str < float` on object dtype: TypeError,
      hard crash. "Run it unchanged" was false.
    - **The JSON API omits null keys entirely.** A record with no borough has no `borough`
      key at all (verified). Paginated chunks therefore carry different column sets;
      concatenating them KeyErrors at line 74 or silently yields an all-NaN column.
      Fix: `reindex(columns=EXPECTED)` at the pull boundary.
    - **Ordering bug:** `borough_missing_but_recoverable_via_lat_long` (lines 76-78) is
      computed BEFORE bad coordinates are nulled (lines 87-96). The headline recoverable
      count currently includes `(0,0)` and out-of-bbox rows. Move it after the scrub, and
      regenerate every number in `docs/FINDING.md` afterward rather than carrying them over.
14. **CRS and axis order, previously unstated.** NYC DCP's borough SHAPEFILE is EPSG:2263
    (State Plane NY Long Island, feet); the Open Data GeoJSON `7t3b-ywvw` is EPSG:4326.
    They are NOT interchangeable. Degrees against 2263 polygons yields ZERO matches, and a
    zero reads as "the recovery failed" rather than "reproject." Same silent zero for
    `Point(lat, lon)` instead of `Point(lon, lat)`.
    **Run the agreement check FIRST, as a build gate, not as a statistic.** Expect high-90s
    percent. Below ~90% means CRS, axis order, or shoreline clipping is wrong, not that the
    method is weak. Gate the phase on it before writing down any recovery number.
15. **Correction to amendment 7's denominator.** "1,577,812 rows carry both a reported
    borough and coordinates" is WRONG. 1,577,812 is borough-labeled rows *period*. The
    actual validation set is **1,533,614** (labeled AND coordinates inside the NYC bbox),
    measured. This repeated the exact coords-vs-labeled conflation caught in amendment 6.
16. **Sequencing, superseding the naive Phase 1 deploy:**
    `pull -> clean -> polygon join -> SCHEMA FROZEN -> one Parquet commit -> chart branches`.
    Until the Parquet lands, chart branches stack on each other rather than merging to
    `main`. Reason: Streamlit auto-redeploys on every push to `main`, the Parquet is
    gitignored until Phase 3, and chart branches read it, so merging early puts a
    `FileNotFoundError` on the public URL. Freezing the schema first also stops decision 9's
    raise-on-unexpected-columns from firing on `borough_recovered`.
17. **Test and CI infrastructure fixes:**
    - Deaths are 3,617 / 2,269,187 = **0.16%** of rows, so the 1.51x ratio test CANNOT run
      on any committable fixture. Emit a few-KB aggregate CSV
      (`borough_source x label_status x rows x deaths`) from the pipeline, commit it, and
      assert against that. It doubles as the artifact `docs/FINDING.md` cites.
    - The year-skew test asserts over the committed `rows_per_year` log, not a live pull.
      Keep the live version as a manual script.
    - **Never write `py` inside a script or workflow.** GitHub Actions ubuntu runners have
      no `py` launcher. README prose only.
    - Gate the `audit_columns.py` Action on the data file existing, or it fails on every
      push while the Parquet is gitignored, putting a permanent red X on the repo.

**Coverage today: 3 of 16 code paths and user flows have a planned test (19%).** The 13
gaps are enumerated in the eng review's coverage diagram; the highest-value untested paths
are `pull_data.py`'s three error branches, the join-yield measurement, the agreement-rate
check, and the zero-result filter state.
